2. Методика тестирования

  1. Разрешение DNS, проверка доступности TCP/80 и TCP/443.
  2. Анализ HTTP-заголовков, TLS-сертификата, политики редиректов.
  3. Проверка наличия защитных заголовков безопасности.
  4. Идентификация CMS и её компонентов по публичным артефактам.
  5. Проверка эндпоинтов REST API на доступ без аутентификации.

3. Находка № 1 — Публично доступный журнал отладки WordPress

Уровень риска:Critical
Адрес:https://stk-96.ru/wp-content/debug.log
Классификация:CWE-532, CWE-219
Аутентификация:не требуется

Описание

По указанному адресу без аутентификации доступен файл журнала отладки WordPress. Файл активно пополняется с 1 сентября 2026 года, на момент проверки его размер превышает 1,1 МБ. Содержимое включает полные серверные пути, названия внутренних файлов ядра CMS, а также сообщения об ошибках уровня PHP Deprecated, PHP Warning и PHP Fatal error.

Почему это критично. Публичный журнал отладки — готовый источник разведданных: структура каталогов, версия ядра, имена пользователей и фрагменты SQL-запросов. На практике такие файлы используются как первый шаг подготовки точечной атаки.

Воспроизведение

Запрос к файлу выполняется обычным GET, без специальных заголовков.

PS> Invoke-WebRequest 'https://stk-96.ru/wp-content/debug.log' -UseBasicParsing -TimeoutSec 10 Status: 200 Content-Type: text/plain Length: 1131997
Фрагмент ответа — первые строки журнала
[01-Sep-2026 13:26:45 UTC] PHP Deprecated: preg_replace(): Passing null to parameter #3 ($subject) of type array|string is deprecated in /home/s/stk96/stk96.beget.tech/public_html/wp-includes/kses.php on line 2025

Чувствительные элементы в ответе

  • /home/s/stk96/stk96.beget.tech/public_html/ — полный серверный путь и имя хостинг-аккаунта;
  • wp-includes/kses.php — точное расположение файла ядра, раскрывает версию CMS;
  • line 2025 — номер строки, позволяет сопоставить код с конкретной версией ядра.

Влияние

  • Раскрытие структуры файловой системы и имени хостинг-аккаунта.
  • Возможное присутствие в файле логина администратора и путей к плагинам.
  • Возможное присутствие фрагментов SQL-запросов и токенов.
  • Облегчение эксплуатации других, ещё не выявленных уязвимостей (LFI, RFI).
  • Файл продолжает пополняться — утечка носит постоянный характер.

Рекомендации

  1. Отключить режим отладки на production в wp-config.php:
    define('WP_DEBUG', false); define('WP_DEBUG_LOG', false); define('WP_DEBUG_DISPLAY', false); define('SCRIPT_DEBUG', false);
  2. Удалить существующий файл wp-content/debug.log.
  3. Закрыть на уровне nginx доступ к *.log в каталоге /wp-content/:
    location ~* /wp-content/.*\.log$ { deny all; return 403; }
  4. Настроить ротацию журналов и вынести их за пределы web-root.

4. Находка № 2 — Устаревшая версия PHP

Уровень риска:High
Компонент:Интерпретатор PHP
Версия:8.1.34
Классификация:CWE-1104 (использование неподдерживаемых компонентов)

Описание

Заголовок X-Powered-By раскрывает точную версию PHP. Ветка 8.1 официально снята с поддержки безопасности 31 декабря 2025 года. С этого момента уязвимости, найденные в данной ветке, не получают патчей.

PS> (Invoke-WebRequest 'https://stk-96.ru' -Method Head -UseBasicParsing).Headers Key Value Server nginx-reuseport/1.21.1 X-Powered-By PHP/8.1.34

Влияние

  • Любая новая CVE в ветке PHP 8.1 останется незакрытой.
  • Совместимость с новыми версиями ядра WordPress и плагинов будет ухудшаться.
  • Публично раскрыта точная версия — упрощает подбор эксплойта.

Рекомендации

  1. Обновить PHP до актуальной поддерживаемой ветки (8.3 или 8.4).
  2. Скрыть версию: в php.ini установить expose_php = Off.
  3. Перед обновлением проверить совместимость плагинов и темы.

5. Находка № 3 — Раскрытие списка пользователей через REST API

Уровень риска:Medium
Адрес:https://stk-96.ru/wp-json/wp/v2/users
Классификация:CWE-200 (раскрытие информации)

Описание

Эндпоинт WordPress REST API возвращает список зарегистрированных пользователей без аутентификации. В ответе раскрывается логин admin, что существенно упрощает подготовку атаки на форму входа.

PS> Invoke-RestMethod 'https://stk-96.ru/wp-json/wp/v2/users' -UseBasicParsing id slug name 1 admin admin

Дополнительно подтверждено: /wp-json/wp/v2/users/me корректно возвращает 401 — то есть защищён. Проблема именно в публичном перечислении пользователей.

Влияние

  • Раскрытие действующего логина администратора.
  • Упрощение брутфорса и password spraying.
  • Возможность таргетированной фишинговой атаки на известного пользователя.

Рекомендации

  1. Отключить публичный доступ к списку пользователей:
    add_filter('rest_endpoints', function($endpoints) { unset($endpoints['/wp/v2/users']); unset($endpoints['/wp/v2/users/(?P<id>[\d]+)']); return $endpoints; });
  2. Переименовать учётную запись admin на нейтральное имя.
  3. Ограничить доступ к REST API для неавторизованных запросов, если API не используется публично.

6. Находка № 4 — Отсутствуют заголовки безопасности

Уровень риска:Medium
Классификация:CWE-693 (недостаточная защита механизма)

Описание

В ответах сервера отсутствуют шесть базовых защитных заголовков. Само по себе это не является прямой уязвимостью, но лишает браузер пользователя ряда встроенных механизмов защиты.

ЗаголовокСтатусНазначение
Strict-Transport-SecurityотсутствуетЗащита от SSL-stripping
Content-Security-PolicyотсутствуетСнижение риска XSS
X-Frame-OptionsотсутствуетЗащита от clickjacking
X-Content-Type-OptionsотсутствуетЗащита от MIME-sniffing
Referrer-PolicyотсутствуетКонтроль утечки Referer
Permissions-PolicyотсутствуетОграничение браузерных API

Рекомендации

Добавить заголовки на уровне nginx:

add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always; add_header X-Content-Type-Options "nosniff" always; add_header X-Frame-Options "SAMEORIGIN" always; add_header Referrer-Policy "strict-origin-when-cross-origin" always; add_header Permissions-Policy "geolocation=(), microphone=(), camera=()" always; add_header Content-Security-Policy "default-src 'self'; script-src 'self' 'unsafe-inline'; style-src 'self' 'unsafe-inline'; img-src 'self' data: https:;" always;

CSP рекомендуется включать в режиме отчёта (Content-Security-Policy-Report-Only) на первой итерации, чтобы не сломать текущую вёрстку.

7. Находка № 5 — Отсутствие двухфакторной аутентификации

Уровень риска:Medium
Адрес:https://stk-96.ru/wp-login.php

Описание

На форме входа не обнаружено признаков наличия второго фактора. В сочетании с раскрытым логином admin и устаревшей версией PHP это повышает ценность успешной компрометации учётной записи.

PS> $lh = (Invoke-WebRequest 'https://stk-96.ru/wp-login.php' -UseBasicParsing).Content PS> $lh -match 'two-factor|2fa|otp|authenticator|totp' False

Рекомендации

  1. Установить плагин двухфакторной аутентификации (TOTP или WebAuthn).
  2. Включить 2FA в первую очередь для всех пользователей с ролью administrator.
  3. Дополнительно ограничить доступ к /wp-login.php и /wp-admin/ по IP.

8. Находка № 6 — Раскрытие версий серверного ПО

Уровень риска:Low
Классификация:CWE-200 (раскрытие информации)

Заголовки ответа содержат точные версии серверного ПО: nginx-reuseport/1.21.1 и PHP/8.1.34. Само по себе это не уязвимость, но упрощает подбор подходящего эксплойта.

Server: nginx-reuseport/1.21.1 X-Powered-By: PHP/8.1.34

Рекомендации

  • Скрыть версию nginx: server_tokens off; в конфигурации.
  • Скрыть версию PHP: expose_php = Off в php.ini.
  • Убедиться, что nginx обновлён до актуальной стабильной ветки.

9. Заключение и приоритеты исправления

Ресурс stk-96.ru функционирует на устаревшей версии PHP, использует CMS WordPress с публично доступным журналом отладки и не применяет базовые защитные заголовки. Совокупность этих факторов формирует устойчивую поверхность для подготовки целенаправленной атаки. Прямой эксплуатации уязвимостей в рамках согласованного объёма не производилось.

Что осталось за рамками работ

В рамках согласованного объёма не проводилось тестирование бизнес-логики, параметров GET/POST на SQL-инъекции и XSS, загрузки файлов, а также аудит сторонних плагинов и тем. При необходимости эти направления могут быть согласованы отдельно.
